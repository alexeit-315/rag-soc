## Контекст

Требуется выбрать платформу CI/CD для автоматизации сборки, тестирования и деплоя RAG SOC Platform.

**Текущее состояние:**
- Репозитории кода размещены на **GitHub** (`rag-soc-core`, `rag-soc-gateway`, `rag-soc-infra`).
- Команда использует GitHub Pull Requests для code review.
- Инфраструктура: on-prem Kubernetes (Istio, Harbor, Keycloak).
- Ограничение поддержки: 0.05 FTE (максимальная автоматизация обязательна).

**Требования:**
- Нативная интеграция с GitHub (без синхронизации репозиториев).
- Поддержка Kubernetes (Helm-деплои, K8s executors).
- Встроенная работа с артефактами (отчёты тестов, security-сканы, coverage).
- Интеграция с Harbor (Container Registry) и Keycloak (OIDC).
- Только Open Source (self-hosted предпочтительно для cost-эффективности).
- Поддержка 0.05 FTE (минимум операционных затрат).

***

## Рассмотренные альтернативы

### 1. GitHub Actions (self-hosted runners)

**Описание:** Нативная CI/CD-платформа GitHub с возможностью использования self-hosted runners в K8s.

**Плюсы:**
- ✅ **Нативная интеграция с GitHub** — нет синхронизации, задержек, дополнительных webhook'ов.
- ✅ **20,000+ готовых actions** — быстрее настройка, меньше кастомных скриптов.
- ✅ **Бесплатные hosted runners** — 2000 мин/мес для private репозиториев (покрывает ~60–70% пайплайнов для MVP).
- ✅ **Проще workflow для команды** — не нужно изучать новый инструмент (PR → Actions → Deploy).
- ✅ **Self-hosted runners в K8s** — полный контроль над ресурсами, кэшированием, артефактами (решает лимиты hosted).
- ✅ **Интеграция с Harbor** — через стандартные `docker/login-action`, `docker/build-push-action`.
- ✅ **OIDC к K8s** — безопасный деплой без долгоживущих kubeconfig (GitHub поддерживает с 2024).
- ✅ **Меньше операционных затрат** — нет дополнительного компонента (GitLab CE), экономия 4 CPU, 8 GB RAM + 0.1 FTE.

**Минусы:**
- ⚠️ **Слабее K8s-интеграция "из коробки"** — нет встроенной команды Helm (но есть `azure/setup-helm`, `bitnami/helm`).
- ⚠️ **Менее удобный UI для отладки** — но для 0.05 FTE это не критично (логи в JSON, артефакты в S3).
- ⚠️ **Лимиты hosted runners** — 2000 мин/мес (решается self-hosted runners для integration/build jobs).
- ⚠️ **Менее DRY-конфигурация** — нет `extends`/`include` как в GitLab (решается через `reusable workflows`).

**Ресурсы для self-hosted runners:**
- 2–3 подов в K8s (по 2 CPU, 4 GB RAM каждый) = **6 CPU, 12 GB RAM** (суммарно).
- Хранение артефактов: GitHub (30 дней) + S3 для долгосрочных (RAGAS-метрики).

***

### 2. GitLab CI (CE, self-hosted)

**Описание:** Self-hosted CI/CD-платформа с нативной поддержкой K8s и Helm.

**Плюсы:**
- ✅ Нативная поддержка Kubernetes (Kubernetes executor, Helm).
- ✅ Встроенная работа с артефактами (отчёты тестов, coverage, security dashboard).
- ✅ DRY-конфигурация (`include`, `extends`, шаблоны).
- ✅ Интеграция с Harbor и Keycloak "из коробки".
- ✅ Бесплатная Community Edition для on-prem.
- ✅ Лучший UI/UX для отладки pipeline.

**Минусы:**
- ❌ **Требуется синхронизация GitHub → GitLab** — webhook + mirror (задержка 1–5 мин, риск рассинхронизации).
- ❌ **MR/PR workflow разорван** — code review в GitHub, pipeline в GitLab (путаница для команды).
- ❌ **Дополнительный компонент (GitLab CE)** — 4 CPU, 8 GB RAM, операционные затраты на поддержку (обновления, бэкапы, мониторинг).
- ❌ **Сложнее onboarding** — команда должна изучать GitLab CI YAML + workflow.
- ❌ **0.05 FTE не потянет поддержку GitLab CE** — критичное ограничение.

**Ресурсы для GitLab CE:**
- 4 CPU, 8 GB RAM (PostgreSQL + Redis + MinIO + GitLab Rails).
- 50 GB PVC (хранилище артефактов, репозиториев).
- ~0.1 FTE на поддержку (обновления, бэкапы, мониторинг).

***

### 3. Jenkins

**Описание:** Классическая CI/CD-платформа с плагинами.

**Плюсы:**
- ✅ Максимальная гибкость (2000+ плагинов).
- ✅ Зрелая платформа (15+ лет).

**Минусы:**
- ❌ **Сложность настройки и поддержки** — требует 0.5+ FTE (не соответствует ограничению).
- ❌ **Громо́здкий UI, устаревшая архитектура** — сложно для онбординга.
- ❌ **Нет встроенной работы с Kubernetes** — требует плагинов (jenkins-kubernetes-plugin).
- ❌ **Частые уязвимости в плагинах** — дополнительная нагрузка на security.

**Ресурсы:**
- 2 CPU, 4 GB RAM (контроллер) + агенты.
- ~0.5 FTE на поддержку (критично не соответствует ограничению).

***

## Решение

**Выбрано:** **GitHub Actions (self-hosted runners в K8s)**.

**Обоснование:**

1. **Нативная интеграция с GitHub** — нет синхронизации, задержек, дополнительных компонентов. Команда работает в едином workflow (PR → Actions → Deploy).
2. **Меньше операционных затрат** — нет GitLab CE (экономия 4 CPU, 8 GB RAM + 0.1 FTE на поддержку). Критично для 0.05 FTE.
3. **Self-hosted runners решают лимиты** — 2000 мин/мес hosted достаточно для lint/unit-тестов, self-hosted для тяжёлых jobs (integration, build, deploy).
4. **Экосистема actions** — готовые actions для Helm (`azure/setup-helm`), K8s (`azure/k8s-set-context`), Harbor (`docker/login-action`), OWASP ZAP (`zaproxy/action-api-scan`), RAGAS (кастомный script).
5. **OIDC к K8s** — безопасный деплой без долгоживущих kubeconfig (GitHub поддерживает OIDC для K8s с 2024).
6. **Проще для команды** — не нужно изучать новый инструмент, workflow единый (PR → Actions → Deploy).

**Компромиссы:**
- Менее DRY-конфигурация (нет `extends` как в GitLab) — решается через `reusable workflows` (вынесение общих шагов в `.github/workflows/templates/`).
- UI проще — но компенсируется артефактами (JUnit, SARIF, JSON) и алертами (Slack/Email).

## Последствия

### Положительные

- **Упрощение архитектуры** — нет GitLab CE, меньше компонентов (экономия 4 CPU, 8 GB RAM).
- **Быстрее onboarding** — команда уже знает GitHub (1–2 дня на изучение Actions YAML).
- **Меньше операционных затрат** — нет поддержки GitLab CE (экономия ~0.1 FTE).
- **Нативный workflow** — PR → Actions → Deploy (единая точка входа, нет рассинхронизации).
- **Богатая экосистема** — 20,000+ готовых actions (быстрее настройка, меньше кастомных скриптов).

### Отрицательные

- **Лимиты hosted runners** — 2000 мин/мес (решается self-hosted для integration/build/deploy jobs).
- **Менее удобный UI** — но компенсируется артефактами (JUnit, SARIF, JSON) и алертами (Slack/Email).
- **Менее DRY-конфигурация** — решается через `reusable workflows` (доп. 4–6 часов на настройку).

### Нейтральные

- Команда должна изучить GitHub Actions YAML (1–2 дня на онбординг).
- Настройка self-hosted runners в K8s (4–6 часов для одного DevOps).
- Настройка OIDC для деплоя в K8s (2 часа).

## План внедрения

| Шаг | Задача | Оценка | Ответственный |
|-----|--------|--------|---------------|
| 1 | Настроить GitHub Secrets (Harbor credentials, OIDC для K8s) | 1 час | DevOps |
| 2 | Развернуть self-hosted runners в K8s (Actions Runner Controller) | 4 часа | DevOps |
| 3 | Настроить кэширование (pip, Gradle, Docker layers) | 2 часа | DevOps |
| 4 | Создать `.github/workflows/ci.yml` (полный pipeline) | 8 часов | DevOps + Lead Dev |
| 5 | Настроить OIDC для деплоя в K8s (без kubeconfig) | 2 часа | DevOps |
| 6 | Протестировать pipeline на staging (полный цикл) | 4 часа | Вся команда |
| 7 | Настроить алерты (Slack/Email) для failed pipelines | 2 часа | DevOps |

**Итого:** ~23 часов (3 рабочих дня для одного DevOps).

| Метрика | Целевое значение | Измерение |
|---------|------------------|-----------|
