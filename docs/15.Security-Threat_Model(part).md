

# Обновление документа п.15 (Security/Threat Model)

## Новый подраздел 4.x: Безопасная разработка в CI/CD

### 4.x.1 Интеграция security-инструментов

| Инструмент | Тип | Стадия | Конфигурация | Действие при находках |
|------------|-----|--------|--------------|----------------------|
| **Semgrep** | SAST | `security` | `--config auto` (builtin rules) | Warning (critical → блокировка после 3 раз) |
| **pip-audit** | SCA | `security` | `--severity high` | Warning (critical → блокировка после 3 раз) |
| **Trivy** (для Docker) | SCA Container | `build` | `--severity HIGH,CRITICAL` | Warning в логах, блокировка при critical > 0 |
| **OWASP ZAP** | DAST | `validate-staging` | API scan по OpenAPI spec | Блокировка prod при High/Critical |

***

### 4.x.2 Политики блокировки

**Уровни уязвимостей:**
- **Critical** — CVE с CVSS ≥ 9.0, RCE, SQLi, XSS.
- **High** — CVE с CVSS 7.0–8.9.
- **Medium** — CVE с CVSS 4.0–6.9.
- **Low** — CVE с CVSS < 4.0.

**Политика:**
| Тип скана | Critical | High | Medium |
|-----------|----------|------|--------|
| SAST (Semgrep) | Блокировка после 3 раз | Warning | Игнор |
| SCA (pip-audit) | Блокировка после 3 раз | Warning | Игнор |
| DAST (ZAP) | Блокировка prod | Блокировка prod | Warning |

***

### 4.x.3 Управление секретами в CI/CD

**Хранение секретов:**
- **GitLab CI Variables:** Masked + Protected переменные для:
  - `HARBOR_USER`, `HARBOR_PASSWORD`
  - `KUBECONFIG_STAGING`, `KUBECONFIG_PROD`
  - API-ключи внешних сервисов
- **K8s Secrets:** Через Helm values (шифрование на уровне etcd).
- **Запрещено:**
  - Хардкод секретов в коде.
  - Передача секретов через environment variables в логах.

**Ротация секретов:**
- Harbor credentials — каждые 90 дней.
- Kubeconfig — при перевыпуске сертификатов K8s (раз в год).

***

### 4.x.4 Аудит и compliance

**Логирование security-событий:**
- Все запуски SAST/SCA/DAST логируются в GitLab CI.
- Отчёты сохраняются в артефактах (90 дней).
- Критические находки отправляются в Slack/Email.

**Compliance-требования:**
- Все образы должны проходить сканирование перед деплоем в prod.
- Деплой в prod только после manual approval (maintainer+).
- История деплоев хранится в GitLab Environments (1 год).

***

### 4.x.5 Disaster Recovery для security

**Сценарий:** Обнаружена critical уязвимость в production-образе.

**Процедура:**
1. Создать hotfix-ветку от последнего стабильного тега.
2. Исправить уязвимость (обновить зависимость).
3. Запустить pipeline в обход стадий `test` (только `lint` → `security` → `build` → `deploy-prod`).
4. Manual approval от Team Lead + Security Engineer.
5. Деплой через canary (10% → 50% → 100%) с ускоренными smoke tests.

**Время реакции:** ≤ 2 часов (RTO для security-инцидентов).
